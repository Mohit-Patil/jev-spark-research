# Jev + Spark: runtime AQE research results

**20 September 2026 | Native Mac mini | Spark 4.0.1 | Jev 1.13.0**

## Executive finding

The project has progressed beyond whole-query plan selection. We implemented and tested capture of actual current/proposed AQE decision states, obtained live Jev responses while Spark was at those boundaries, and executed controlled, single-boundary AQE interventions on synthetic queries.

**The integration is feasible. A useful Jev-driven optimization has not been demonstrated.** Six live runtime recommendations all abstained. Their measured HTTP round trips were 0.973-1.740 seconds, whereas observed plan-choice differences were generally milliseconds. Two fixed-arm runtime trials disagreed on the direction of a small timing effect. A separate candidate-coverage audit showed that a useful whole-query alternative was absent from the actual current/proposed pairs for the retained-skew workload.

The durable API ledger ends this continuation at **19 of 50 attempts used; 31 remain**. This continuation made six new requests, attempts 14-19. Attempts 12-13 were already present in the shared research workspace and are included in the cumulative accounting, not claimed as executions initiated here.

## 2. A benchmark defect was found and corrected

The earlier harness deduplicated candidates by their initial physical-plan fingerprint. That is not sufficient for whole-query variants carrying different join hints: the initial physical plans can be identical while future AQE behavior differs.

We observed exactly that. `NATIVE` and `MERGE` initially both used sort-merge join. On the selective workloads, native AQE subsequently used broadcast hash join, while the MERGE-hinted query retained sort-merge join. Removing MERGE as an initial-plan duplicate would therefore remove a genuinely different execution policy.

The corrected inventory retains `NATIVE`, `BROADCAST`, `MERGE`, and `SHUFFLE_HASH`, while recording initial-plan collisions. A regression test checks both retention under mocked collisions and the actual saved divergence. The original frozen pilot was preserved rather than silently rewritten.

## 3. Whole-query headroom exists in some development cases

The corrected screen used 1.2 million fact input rows and 2 million unfiltered dimension input rows. It first varied dimension selectivity at fixed seed 313, then varied the input hot-key distribution. Each strategy had two warmups and seven measured repetitions per case, with randomized execution order.

| Development case | Native median | Broadcast | Merge | Shuffle hash |
|---|---:|---:|---:|---:|
| 1% dimension selectivity | 83.80 ms | 69.88 ms | 77.89 ms | 60.77 ms |
| 10% dimension selectivity | 159.14 ms | 97.88 ms | 111.06 ms | 101.75 ms |
| 50% dimension selectivity | 199.48 ms | 225.29 ms | 198.73 ms | 254.63 ms |
| 50% selectivity, retained 80% hot-key input | 252.29 ms | 213.29 ms | 255.22 ms | 247.32 ms |

The 0.75 ms native/MERGE difference at 50% selectivity is not useful evidence of an advantage. Timing variability was substantial in some selective runs. The first screen and corrected screen did not always identify the same fastest strategy. These are development observations, not held-out generalization or production speedup claims.

The worst single corrected-screen alternative regression was SHUFFLE_HASH at 50% selectivity: **1.375 times its same-round native time, or 72.62 ms slower**. This is an observed noisy execution, not a universal regression rate.

These timings include SQL construction, initial-plan capture and collection. They exclude enumerating all candidates, final-plan logging, and any Jev request. Inputs were uncached generated Range data in a warmed shared JVM; OS/JIT/GC state was not reset. A hinted whole-query gain is not the counterfactual gain of switching after earlier work has already completed.

## 4. Real runtime AQE observation now works

The saved Spark 4.0.1 source and installed bytecode identify consecutive cost-evaluator calls in `AdaptiveSparkPlanExec.scala`: current at line 365, proposed at line 366. The referenced release commit is `29434ea766b0fc3c3bf6eaadb43a8f931133649e`. The bytecode dump, source digest and compiler records are preserved.

`NativeBoundaryObserverV2` delegates to Spark's stock SimpleCostEvaluator and returns the stock cost unchanged. It pairs calls using the evaluator instance, thread, checked source location and run tag. It records the two remaining plans, visible stage materialization state, actual runtime rows and size statistics, reported shuffle partition bytes, and the native comparison result.

The 36-query check captured **63 pairs / 126 cost calls**, with zero unmatched calls, errors or dropped records. All query results and reconstructed native decision predicates checked out. Median observer self-time was **2.372 ms/query** on the selective case and **1.413 ms/query** on the retained-skew case. Randomized paired whole-query overhead medians were approximately **1.486 ms** and **1.387 ms**; these include normal timing variability.

An actual medium-selectivity snapshot had a completed dimension stage with **200,000 rows**, Spark-reported runtime size **4,800,000 bytes**, and reported shuffle partition-byte total **1,873,358 bytes across eight partitions**. The other stage was unfinished and its unavailable values remained null. Current was sort-merge; proposed was broadcast hash join.

The two captures are consecutive observations, not an atomic freeze of all tasks. Visible stage leaves are not a complete history of executed work. Runtime size statistics, serialized partition-byte reports, and in-memory hash-table size are distinct quantities. The hook is version-specific research code, not a stable general-purpose pairwise Spark API.

## 5. Live Jev advice was requested inside the AQE loop

A bounded loopback callback sent the captured synthetic state to the existing request-budgeted adapter while Spark was inside the proposed-plan cost call. The observer still returned the native cost; it did not apply the advice. The server and its thread were closed within the tracked job.

Three queries each received two feature views: PLANS, then PLANS plus explicit runtime STATS. Both used the same captured boundary state and the choices CURRENT / PROPOSED / ABSTAIN. Native decision labels, stock costs and future candidate outcomes were excluded. Plans themselves encode runtime adaptations, so PLANS is not a completely runtime-information-free ablation.

| Case | Plans-only response / latency | With-statistics response / latency |
|---|---|---|
| Small selective input | ABSTAIN / 1.132 s | ABSTAIN / 0.973 s |
| Medium selective input | ABSTAIN / 1.041 s | ABSTAIN / 0.979 s |
| Hot-key-generator input with hot key filtered out | ABSTAIN / 1.740 s | ABSTAIN / 1.022 s |

All six calls succeeded and completed before their query finished. They used 14,639 input tokens and 264 output tokens. Median observed HTTP latency was **1.031 s**. The adapter used a fresh HTTP client/connection per request; this is network/TLS/client/server round-trip time, not an isolated model-inference measurement. Connection pooling and same-request multi-question comparison have not been benchmarked.

All three query results were correct, with 12 recorded boundary pairs and no callback errors. Running both views added roughly 2.04-2.77 seconds of observer/callback self-time per query. These diagnostic timings are not optimized-policy speedups.

Six abstentions do not establish zero accuracy or prove that Jev cannot help another workload. They show no positive selection signal under these inputs and this cautious prompt. The prompt was not repeatedly tuned to force a favorable answer.

## 6. Actual single-boundary interventions and replication

`NativeBoundaryObserverV3` is a separate, no-network experimental adapter. It can retain CURRENT once at a preregistered target where stock Spark would choose PROPOSED. It changes only that one comparison's returned cost. Other boundaries and unmatched runs use the native decision. PROPOSED is the unchanged native branch at the same target.

The target was taken from the earlier medium-selectivity live snapshot, before these branch outcomes existed. Its signature is:

`6346d36add42a6bc04a73ca67edebcef3361923148a3b51fd904b48e950e4589`

The signature covers normalized current/proposed remaining plans and all recorded visible-stage fields, including materialization flags, row counts, size statistics and partition-byte arrays. Python and Scala recomputed matching hashes. The trial froze its target, sources, data, sample count and randomized arm order before execution. The replication kept those substantive choices fixed and changed only output location, random seed and sample count.

| Trial | Measured runs per arm | CURRENT state matches | PROPOSED state matches | Rounds where both matched | Paired remaining-time finding |
|---|---:|---:|---:|---:|---|
| First trial | 10 | 8 | 6 | 4 | CURRENT slower in 4/4; median penalty 5.15 ms |
| Fixed replication | 30 | 15 | 22 | 11 | CURRENT faster in 9/11; median saving 2.26 ms |

Across both trials, **26 actual fixed-arm AQE interventions** occurred, including warmups. Every result remained correct. Final joins were broadcast hash joins in both arms: retaining CURRENT for one decision does not force sort-merge for the entire query, and later native AQE can still change plans.

**There is no stable demonstrated runtime advantage.** The paired direction changed between batches. Per-arm matched medians are not a substitute for comparing rounds in which both branches reached the same observed target. In the replication, the worst matched CURRENT regression was **13.43% / 11.74 ms** relative to PROPOSED. All missed-state runs are retained as native fallbacks, not discarded from overall attempt counts.

Matching observed state does not match in-flight task progress, JVM/GC state, or OS scheduling. Remaining-time measurement also includes one JVM clock RPC after collect; its median was roughly 0.17-0.18 ms. The few-millisecond effect is near instrumentation and execution variability. These are exploratory fixed-arm interventions, not Jev-chosen interventions or broad causal/performance validation.

## 7. Candidate availability is a separate limitation

The retained-skew observation workload is the same generator case where the whole-query broadcast variant showed headroom. Its **27 recorded AQE comparisons offered no broadcast plan**: current and proposed were equal sort-merge plans in all 27. There were zero structurally changed pairs.

A selector restricted to CURRENT / PROPOSED cannot select an alternative absent from both. This is a concrete candidate-generation limitation, not merely an inaccurate ranking function. Constructing an additional legal remaining-work alternative would need to account for existing materialization, extra exchanges and memory; the whole-query broadcast result does not establish its runtime benefit.

A related workload audit found that the live case named `live_skew` used seed 733 with a 50% dimension filter, which removes the hot key. It is therefore not evidence about surviving intermediate skew. The retained-skew development/observer cases used seed 313, where the hot key survives. The original artifacts are preserved and the distinction is explicit rather than silently changing labels.

## 8. Cost, evidence status and next research branch

All 19 recorded Jev attempts succeeded and report a cumulative **44,739 input tokens and 963 output tokens**. At the official published price of $0.042 per million input tokens, with output free, this is an arithmetic estimate of **$0.001879**, not an inspected invoice. The six new calls alone correspond to approximately $0.000615. Latency, not the token bill, is the observed obstacle on these sub-second queries.

**Measured:** corrected whole-query comparisons; real runtime statistics; observer self-time; in-loop Jev responses; actual fixed-arm AQE changes; exact result equivalence; request counts and token usage; variable state-match rates and branch effects.

**Estimated:** token cost at the published rate. No estimated selector time is presented as a measured end-to-end speedup.

**Not established:** a Jev-selected faster branch, a Jev-directed live override, a generalizable prediction policy, reliable advantage on held-out query families, production safety, cluster-scale behavior, optimized connection-pool latency, or a complete executed-prefix replay mechanism.

The next research branch should address candidate availability and reproducible observed-state comparisons before spending the remaining allowance on repeated prompt variations. It needs richer legal remaining-plan alternatives, longer-running synthetic work with meaningful potential savings, and tighter accounting of concurrent stage progress. Native Spark should remain the comparator. The completed interface and traces support that work; the current evidence does not justify deploying a remote Jev call on every AQE decision.
